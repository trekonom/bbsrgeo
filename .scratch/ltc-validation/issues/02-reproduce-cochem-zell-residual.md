# Reproduce the Cochem-Zell to Rhein-Hunsrück residual; tighten ltc test tolerances

Status: done
Category: bug

Found in review of commit b0e071a (`tests/testthat/test-validate-ltc.R`, vignette).

The ~1.2-1.3% Rhein-Hunsrück gap is attributed to INKAR "evidently" not applying BBSR's 2013->2014 ~1.7% boundary correction. No code verifies this. The test then accepts median < 0.005, >= 98% within 1%, and max < 0.05; a 5% ceiling can hide a real regression.

Fix: reproduce the gap with and without that transfer; then assert on an explicit set of expected-outlier districts and tighten the generic bounds. (Root cause over tolerance.)

## Agent Brief (ready-for-human)

**Category:** bug (retitle: the documented cause of the Rhein-Hunsrück residual is wrong)

**Why this is not delegated:** it hinges on a design decision: keep `popregio$population_total` as the `care_rate` denominator and document the difference, or rebuild `ltcregio` with a denominator consistent with INKAR's.

**Verified findings**
- For AGS 07140000 (Rhein-Hunsrück-Kreis), `harmonize_regions(type = "ratio")` returns 3.23 / 3.51 / 6.70 for 2009 / 2013 / 2023, identical to raw `ltcregio`. INKAR has 3.19 / 3.46 / 6.70. The gap exists before any conversion.
- The Cochem-Zell (07135000) -> 07140000 2013->2014 transfer (share_population 0.0172, population_old 1.1 vs 101 for the district) is a ~1% weight and shifts the rate by ~0.006 (~0.2%). Removing the row and renormalizing leaves the output unchanged. It does not explain the gap.
- Cause: the denominator. `popregio$population_total` is 102,878 (2009) and 101,854 (2013); `popinkar` is 104,156 and 103,096. The ratios (1.0124, 1.0122) match the ~1.2% gap. In 2023 both are 106,390 and the rates agree. Likely the pre-/post-Zensus-2011 revision (census attribution not confirmed).
- Raw `ltcregio` vs `ltcinkar` across districts: median relative difference ~0.0001, 10th-90th percentile about +/-0.14% in every year.

## Grilling outcome (supersedes the Agent Brief's "Required changes")

Re-checked on harmonized output (all 8 years, 400 districts per year, `harmonize_regions()` ratio and counts-then-divide vs `ltcinkar`/`popinkar`). The brief's denominator explanation does not hold:

- Raw `popregio` vs `popinkar` population differs in only 8 districts (Cochem-Zell, Rhein-Hunsrück, six Thuringian). These are boundary adjustments in INKAR, not a census revision (2021/2023 match exactly).
- After harmonization the Thuringian gaps vanish (rate within 0.3%). Rhein-Hunsrück's harmonized population matches `popinkar` within 0.2%, yet its rate is still 1.2-1.4% off (2009, 2011, 2013). So the denominator is not the cause; rebuilding `ltcregio` with another denominator would not close it.
- INKAR's indicator 280 methodology could not be found in primary sources (`.scratch/ltc-validation/research/inkar-280-methodology.md`). The idea that INKAR leaves the numerator unadjusted is unverified and must not be stated as fact.

Decisions (user):
1. `ltcregio` keeps the `popregio` `population_total` denominator. No rebuild.
2. Test bounds: replace the median / 98%-within-1% / 5%-max assertions with one generic bound, max relative difference < 0.6%, for all districts outside the exclusions.
3. Keep the existing share-sum-anomaly exclusion (07135, 07137). Name Rhein-Hunsrück (07140000), 2009-2013, as a known residual (about 1.3%) with the reason "unexplained; INKAR method undocumented", and no assertion about the mechanism.
4. No ADR, no GLOSSARY.md.

Required changes:
1. Remove the "INKAR does not apply the Cochem-Zell transfer" explanation from `tests/testthat/test-validate-ltc.R`, `vignettes/bbsrgeo.Rmd` (shared with issue 01) and `?ltcregio` (`R/data.R`); replace it with the narrow, verified statement above.
2. Implement decisions 2 and 3 in `test-validate-ltc.R`, covering all `ltcregio` years the test uses.
3. Ask BBSR how indicator 280 is built (follow-up, not blocking).
