## Observation

Reading the cached files with `bbsr_crosswalk_read()` (downloads of 2026-10-24)
still warns for 9 `ags_old`/`year_from` combinations. The check
(`bbsrgeo_check_share_sums()`) looks at area shares only, and its text says
the deviation "is more often caused by inconsistencies in the BBSR source
file itself". Per file:

| File | Combinations | Area share sum | What the rows look like |
| --- | --- | --- | --- |
| `ref-gemeinden-1990-2000.xlsx` | 12039430, 12043470, 15321210 (1992), 01060102 (1996) | 2 | `share_area` and `share_population` are 1 on both target rows; `area_old` and `population_old` differ between the rows (e.g. 12039430: 15.099 / 6.471 km2, 0.48 / 0.21) |
| `ref-gemeinden-2010-2020.xlsx` | 09377444 (2016) | 0.99 | three target rows with `share_area` 0.33 each, `area_old` 5.08 on each, `population_old` 0 |
| `ref-kreise-1990-2024.xlsx` | 07135000, 07137000 (2014, 2015) | 0.962 and 0.038 | one row each (self-mapping) with `share_population` 0.983 and 0.017 |

`harmonize_regions(type = "absolute")` already handles all three patterns
(municipal issue 05: counts as parts when they differ, area split for
zero-population units; ltc-validation 07: renormalization with a warning for
single-row groups). So the reader warns about rows whose downstream effect is
documented. Issue 05 lists all five municipal combinations: 09377444 has
`population_old` 0 (checked); for the four 1990-2000 units the "share of 1 on
every row" convention is likely but not verified there.

## Agent Brief

**Category:** enhancement
**Summary:** `bbsr_crosswalk_read()`'s share-sum warning stops firing on a sum that is only rounding, and names the pattern of each remaining deviation instead of attributing all of them to the source file.

**Current behavior:**
`bbsrgeo_check_share_sums()` warns once, aggregated, for every `ags_old`/transition whose area shares deviate from 1 by more than `SHARE_SUM_TOLERANCE` (0.01). Three problems:
1. A sum of exactly 0.99 (three shares of 0.33, municipal 09377444, 2016) warns, because the floating-point deviation 0.010000000000000009 exceeds 0.01.
2. The text says the cause is "more often ... inconsistencies in the BBSR source file itself" for every case, including ones that `harmonize_regions()` resolves from the counts.
3. It shows one example only, so the reader cannot tell which patterns occur.

**Desired behavior:**
- A deviation of exactly the tolerance is not reported, and the same bound is used by `renormalize_forward_shares()` so the reader and `harmonize_regions()` agree on which groups are deviations.
- The warning names the pattern of the remaining combinations, from what is observed in the rows and without stating a cause. At least: (a) share 1 on every target row of a multi-row group, with counts that differ between rows; (b) a single target row with a share below 1; (c) any other deviation.
- It reports how many combinations fall in each pattern and gives one example for each. It still says to check the original file.
- No change to which rows `harmonize_regions()` renormalizes or how.

**Key interfaces:**
- `bbsrgeo_check_share_sums()`: new message and pattern classification.
- `SHARE_SUM_TOLERANCE` and every comparison against it (the check and `renormalize_forward_shares()`).
- `GLOSSARY.md` **Share deviation**: already updated in the triage commit; keep the code's wording consistent with it.

**Acceptance criteria:**
- [ ] Reading the municipal 2010-2020 file no longer warns for 09377444 (2016).
- [ ] Reading the municipal 1990-2000 file warns once, naming pattern (a) with a count of 4 and an example.
- [ ] Reading the district file warns once, naming pattern (b) with a count of 4 and an example.
- [ ] Tests on small constructed tibbles (the check is internal) cover: sum exactly at the tolerance (no warning), each of patterns (a), (b), (c), and a clean group (no warning).
- [ ] The real-file test in `test-crosswalk-read.R` still passes; update its comment if the warning text it mentions changes.
- [ ] `harmonize_regions()` output is unchanged for all existing tests.

**Out of scope:**
- Recomputing shares from the absolute values (a separate decision: it reopens the rejection recorded in issue 05, where 25 of 27 split groups in the 2020-2024 file carry the unit's total, not the part, in the counts).
- Correcting the BBSR data, including recoding the 2014 and 2015 district rows.
- Changing how `harmonize_regions()` renormalizes.
